- (direction) Modo express escolhido pelo usuário; fonte: README.md; slug catalogo-api.
- (decision) Why: app de validação do TCC — provar que um serviço real segue ponta a ponta o contrato do Golden Path da plataforma (build, segurança, deploy GitOps, observabilidade).
- (capability) CAP-1 cadastrar produto: cliente cria produto via HTTP; sucesso = POST válido persiste e retorna 201 com recurso; inválido retorna 400.
- (capability) CAP-2 listar produtos: cliente obtém lista de produtos cadastrados; sucesso = GET retorna 200 com todos os produtos persistidos.
- (capability) CAP-3 detalhar produto: cliente obtém um produto por id; sucesso = GET por id existente retorna 200, inexistente 404.
- (capability) CAP-4 editar produto: cliente atualiza um produto existente; sucesso = alteração persistida e visível no detalhe; id inexistente 404; inválido 400.
- (capability) CAP-5 remover produto: cliente exclui produto; sucesso = após remoção o detalhe retorna 404; id inexistente 404.
- (capability) CAP-6 health check: plataforma verifica saúde do serviço; sucesso = GET /health retorna 200 quando saudável e não-200 quando o banco está indisponível.
- (capability) CAP-7 telemetria: operador vê traces do serviço no backend de observabilidade; sucesso = requisição HTTP gera trace OTLP com spans ASP.NET Core e EF Core.
- (decision) Banco: PostgreSQL (escolha do usuário).
- (decision) Produto mínimo: Id, Nome, Descrição, Preço, Estoque, CriadoEm, AtualizadoEm (escolha do usuário).
- (decision) Autenticação/autorização é non-goal (escolha do usuário).
- (constraint) Stack: ASP.NET Core, persistência via EF Core (README cita auto-instrumentação EF Core).
- (constraint) Imagem de contêiner linux/arm64, usuário não-root, com health check, via Dockerfile padronizado na raiz.
- (constraint) OpenTelemetry SDK .NET + auto-instrumentação ASP.NET Core/HttpClient/EF Core, exportando OTLP.
- (constraint) Manifestos Kubernetes não ficam no repo: overlay em tcc-platform/apps/catalogo-api.
- (constraint) Segredos não ficam no repo: OCI Vault via ExternalSecret no tcc-platform; app lê config do ambiente.
- (constraint) CI: ci.yml chama backend-service.yml de tcc-pipeline-templates (testes -> Trivy -> imagem GHCR -> commit de tag no tcc-platform -> Argo CD); exige testes automatizados executáveis e secret PLATFORM_REPO_TOKEN.
- (note) Gatilho push/pull_request do ci.yml está desligado até existirem código e Dockerfile; ligar faz parte da entrega.
- (assumption) Contrato REST JSON: POST/GET /produtos, GET/PUT/DELETE /produtos/{id}.
- (assumption) Trivy bloqueia vulnerabilidades críticas/altas; imagem base e dependências precisam passar sem achados bloqueantes.
- (assumption) Validação: nome obrigatório, preço >= 0, estoque >= 0.
- (question) Paginação/filtro na listagem (CAP-2) está no escopo?
- (question) Como o schema é criado/migrado no cluster (migrations EF no startup, job, ou manual)?
- (question) Remoção (CAP-5) é física ou lógica (soft delete)?
- (question) Qual backend de observabilidade recebe o OTLP e qual variável configura o endpoint?

- (decision) Resposta usuário: listagem (CAP-2) tem paginação, filtro e ordenação — supera CAP-2 anterior; sucesso passa a cobrir os três.
- (assumption) Paginação: parâmetros page/pageSize, padrão 20, máximo 100; resposta traz itens + total.
- (assumption) Filtros: nome (contém, sem diferenciar maiúsculas) e faixa de preço (min/max).
- (assumption) Ordenação: campo nome, preco ou criadoEm; direção asc/desc; padrão nome asc; campo inválido retorna 400.
- (decision) Resposta usuário: migrations EF Core aplicadas no startup da aplicação.
- (decision) Resposta usuário: remoção (CAP-5) é lógica (soft delete); produto removido some de listagem/detalhe/edição (404) e registra DeletadoEm.
- (assumption) Sem endpoint de restauração de produto removido.
- (decision) Observabilidade resolvida via tcc-platform: Grafana Alloy no cluster recebe OTLP e envia ao Grafana Cloud; golden-path/base Deployment injeta as variáveis OTel. App só lê variáveis OTEL_* padrão do ambiente, sem endpoint fixo no código.

- (constraint) Migrations no startup implicam que a app precisa permissão DDL no PostgreSQL e startup tolerante a réplicas concorrentes.
