- (direction) Modo Coaching escolhido; spine é a única entrega (no máximo comentada brevemente). Fonte: spec-catalogo-api (SPEC.md + produto.md + golden-path.md + memlog).
- (constraint) Herdado do spec: ASP.NET Core + EF Core + PostgreSQL; migrations no startup tolerantes a réplicas concorrentes; soft delete via DeletadoEm; enums tipados por nome (case-insensitive, 400 fora do enum); config só do ambiente; contrato Golden Path (arm64 não-root, OTel OTLP via OTEL_*, CI compartilhada, manifestos/segredos no tcc-platform).
- (constraint) backend-service.yml: dotnet-version default 9.0.x (input sobrescrevível), test-command default 'dotnet test --configuration Release' na raiz, Dockerfile na raiz, build linux/arm64 via QEMU, Trivy fs+imagem falha só em CRITICAL com fix disponível (corrige assumption do spec: não bloqueia HIGH).
- (constraint) Consumidor conhecido: catalogo-front (Angular) no mesmo cluster; ingress Kong; segredos nomeados <AMB>-TCC-<APP>-<CHAVE> no OCI Vault.
- (version) .NET 9 (STS) e .NET 8 perdem suporte em 2026-11-10; .NET 10 LTS suportado até 2028-11-14 (dotnet.microsoft.com support policy, verificado 2026-10-13). Npgsql.EntityFrameworkCore.PostgreSQL 10.0.x estável (10.0.2 visto no NuGet); Npgsql.OpenTelemetry 10.0.1.
- (decision) Runtime .NET 10 LTS; ci.yml passa dotnet-version: '10.0.x' ao template (template compartilhado inalterado). Previne: build/test em SDK diferente do runtime da imagem; runtime sem patches após 2026-11-10.
- (decision) Paradigma: arquitetura em camadas clássica (Controller -> Service -> Repository -> EF Core), escolhida pelo usuário sobre fatias verticais (A, recomendada) e Clean/Hexagonal (C).
- (version) EF Core 9+ Database.Migrate() adquire lock exclusivo antes de aplicar migrations (docs EF Core 9 'What's new'; Npgsql via LOCK TABLE __EFMigrationsHistory segundo fonte terceira) — cobre réplicas concorrentes sem mecanismo próprio.
- (decision) Fronteiras de dados: Controller só conhece DTOs de request/response; Service converte DTO<->entidade; Repository só conhece a entidade Produto. Previne: entidade EF/DeletadoEm vazando no contrato HTTP.
- (decision) Erros: Service lança exceções de domínio personalizadas; middleware global único as traduz para HTTP. Previne: cada controller mapear erro do seu jeito.
- (question) Usuário propõe status 'desativado' com API retornando todos e front diferenciando — conflita com CAP-5 do spec (removido some da listagem, 404 em consulta/edição). Esclarecer: substitui DELETE? enum de status? reativação? edição de desativado? filtro por status?
- (decision) Estrutura: projeto único CatalogoApi com camadas em pastas (Controllers/Services/Repositories/Data/...) + projeto de testes; solução na raiz (pipeline roda dotnet test na raiz). Regra de dependência só por convenção/arquitetura, não pelo compilador.
- (decision) CAP-5 redefinido pelo usuário (aceitou sugestão): campo Status enum StatusProduto {Ativo, Desativado} substitui DeletadoEm; PATCH /produtos/{id}/status alterna (reativação permitida); DELETE fora de escopo; listagem traz todos por padrão com filtro opcional status; produto desativado continua editável e consultável (200). Sem filtro global do EF.
- (decision) Validação: DataAnnotations nos DTOs de request para formato (400 automático em ProblemDetails); regras de negócio no Service via exceção de validação personalizada traduzida pelo middleware.
- (decision) Contrato de erro: toda resposta de erro é ProblemDetails (RFC 9457), tanto do middleware quanto do 400 automático de model binding.
- (event) Conflito com spec: CAP-5, produto.md (DeletadoEm, regras de 404) e non-goal 'restauração' precisam ser atualizados no spec-catalogo-api.
- (decision) Id: int identity gerado pelo banco.
- (decision) Listagem: envelope { itens, total, page, pageSize }; JSON camelCase; enums como string (nome).
- (decision) Datas: DateTimeOffset UTC, ISO-8601 no JSON; CriadoEm/AtualizadoEm definidos pelo Service.
- (decision) CORS: origens permitidas lidas do ambiente (Cors__OrigensPermitidas), nada fixo no código; consumidor catalogo-front em outro host.
- (decision) Imagem: mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled, porta 8080, usuário não-root da imagem; HEALTHCHECK do Dockerfile invoca o próprio binário (dotnet CatalogoApi.dll --healthcheck -> GET localhost:8080/health, exit 0/1). Kubernetes usa probes do golden-path/base.
- (decision) /health: endpoint único com check do banco (CAP-6); sem split liveness/readiness.
- (decision) Testes: integração via WebApplicationFactory + Testcontainers PostgreSQL (Docker do runner); unidade no Service; sem provider in-memory/SQLite.
- (decision) OpenAPI: Microsoft.AspNetCore.OpenApi nativo, enums como string; sem Swashbuckle.
- (version) OpenTelemetry.Instrumentation.EntityFrameworkCore ainda pré-release (1.15.x-beta, convenções experimentais) — aceito pelo contrato do Golden Path; Testcontainers.PostgreSql 4.13/4.14 (nuget.org 2026-08). Versões exatas ficam com o código.
- (question) Onde roda o PostgreSQL (no cluster ou gerenciado na OCI) e qual versão — pertence ao tcc-platform; app só recebe connection string.
- (decision) Detalhes fixados na destilação: exceções ProdutoNaoEncontradoException(404)/RegraNegocioException(400); /health 503 com banco fora; Preco numeric(12,2); nomes de DTO e tipos por camada; termos de domínio em PT, sufixos técnicos em EN; AtualizadoEm muda também em mudança de status; modo --healthcheck não sobe servidor nem roda migrations.
- (decision) Reviewer gate (rubric, versões, adversário) — achados aplicados: respostas de escrita fixadas; ProblemDetails também para 404/405/415 (AddProblemDetails+UseStatusCodePages, rotas {id:int}); enums rejeitam inteiros e JSON único para MVC+Http.Json (OpenAPI lê Http.Json); campos obrigatórios tipo-valor anuláveis+[Required]; limites espelhados DTO/EF; precoMin<=precoMax; PUT substituição total; CORS parse/métodos/dono; desempate por Id; ILIKE; Status persistido como string; Dockerfile cross-compile BUILDPLATFORM; HEALTHCHECK exec form; migrations sempre transacionais; versões do Stack atualizadas (OTel 1.19, Testcontainers 4.16, Npgsql 10.0.3).
